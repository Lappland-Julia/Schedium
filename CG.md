# Coding Guidelines — Schedium

Этот документ фиксирует стиль кода проекта и порядок работы, использованный при реализации `score`.
Явные указания пользователя для конкретной задачи имеют приоритет над этим руководством.

## Основной принцип

Писать код максимально похожим на существующий: простым, прямым и понятным при чтении сверху вниз.
Изменение должно решать поставленную задачу и сохранять привычную структуру проекта.

- Сначала посмотреть соседние методы и использовать тот же способ оформления и работы с данными.
- Предпочитать обычные условия, циклы, стандартные контейнеры и небольшие методы.
- Не вводить новые слои, интерфейсы, шаблоны и вспомогательные классы без конкретной необходимости.
- Не переписывать соседний код и публичный API ради собственного представления о стиле.
- Использовать возможности современного C++, если они делают код проще и уже приняты в проекте.
- Не добавлять комментарии в код. Объяснения алгоритмов и поведения размещать в README и сообщениях о работе.

## Имена и структура

- Переменные, поля, параметры, методы и тестовые функции называть в `snake_case`.
- Использовать содержательные имена: `gap_duration`, `overlap_penalty`, `current_start`, `latest_end`.
- Новое значение параметра называть с префиксом `new_`: `new_gap_score`, `new_gap_duration`.
- Сохранять принятые имена типов и файлов: `Validator`, `ScheduleEntry`, `ScheduleManager`, `.hpp` и `.cpp`.
- Для чтения использовать принятый префикс `get_`, для изменения — `set_` или `update_` по смыслу и соседнему API.
- Константы и макросы оформлять в принятом для них верхнем регистре.
- Объявления класса размещать в `.hpp`, реализацию с условиями и циклами — в `.cpp`.
- Простые геттеры оставлять внутри класса одной строкой.
- В классах сохранять порядок `private:` затем `public:` и обращение к полям через `this->`.
- Связанные геттер и метод изменения располагать рядом, группы методов разделять пустой строкой.

## Форматирование

Точные правила задают `.clang-format` и `.editorconfig`. Использовать их, а не настройки форматирования по умолчанию.

- Четыре пробела на уровень отступа; табуляцию не использовать.
- Длина строки — до 120 символов, переносы оформлять через clang-format.
- Открывающую фигурную скобку ставить на той же строке, что и объявление, условие или цикл.
- В новых условиях и циклах использовать фигурные скобки, не размещать их тело в одной строке.
- Ссылки и указатели писать как `Type &name` и `Type *name`.
- Метки `private:` и `public:` выравнивать с объявлением класса; `case` писать с отступом внутри `switch`.
- Сохранять порядок и группы `#include`; автоматическую сортировку не включать.
- В `.cpp` сначала включать собственный заголовок, затем после пустой строки остальные заголовки.
- Не добавлять больше одной пустой строки подряд.
- Использовать UTF-8, окончания строк LF и перевод строки в конце файла.

Пример принятого оформления:

```cpp
std::int64_t get_gap_score() const { return this->gap_score; }
void update_gap_score(const std::int64_t &new_gap_score);
```

```cpp
void Validator::update_gap_score(const std::int64_t &new_gap_score) {
    if (new_gap_score < 0) {
        throw std::invalid_argument("Gap score must not be negative");
    }
    this->gap_score = new_gap_score;
}
```

## Реализация

- Сначала проверять входные значения, затем изменять состояние объекта.
- При ошибке настройки сохранять прежние значения и использовать принятые стандартные исключения.
- Для неизменяемых значений использовать `const`; для чтения объектов без копирования — `const auto &`.
- Сигнатуры новых методов оформлять по образцу соседних. Не менять привычную передачу параметров без необходимости.
- Не возвращать ссылку, если она может пережить объект, которому принадлежит значение.
- Выбирать тип по диапазону данных. Для счёта и его параметров использовать `std::int64_t`.
- Время и длительность хранить через `std::chrono`, с явными единицами измерения.
- Перед потенциальным переполнением проверять границы, а не проверять уже переполненный результат.
- Убирать дублирование расчёта: методы, зависящие от одной оценки, должны использовать одну реализацию.
- Настраиваемые величины хранить в полях с понятными значениями по умолчанию и простыми методами изменения.
- Если задача не задаёт значения по умолчанию, выбрать обоснованные значения и сообщить о них до реализации.
- Проверять сложные случаи простым алгоритмом. Не заменять корректный подсчёт приближением ради короткого кода.

## Порядок работы

1. Прочитать задачу, текущий код, настройки CG и состояние Git. Учитывать существующие незакоммиченные изменения.
2. Если нужна ветка, создать её с указанным пользователем допустимым именем и учитывать последующие уточнения.
3. Кратко описать выбранное поведение, параметры и существенные допущения. Обычные решения внутри согласованной задачи принимать самостоятельно.
4. Для изменения поведения сначала добавить или обновить содержательные тесты и увидеть ожидаемое падение на старой реализации.
5. Написать простую реализацию в существующих файлах и стиле проекта.
6. Запустить весь набор тестов и убедиться, что проходят как новые сценарии, так и прежние.
7. Обновить связанные примеры, README, бенчмарк и подписи CI, если изменение делает их неактуальными.
8. Проверить форматирование, подходящие сборки и итоговый diff. Провести ревью поведения и граничных случаев.
9. Сообщить, что изменилось, какие проверки выполнены и что осталось непроверенным.

## Тесты, бенчмарк и документация

- Тестировать наблюдаемое поведение с независимо определёнными ожидаемыми результатами.
- Для расчётов проверять точные значения, а не только общий признак успешности.
- Покрывать границы условий, пустой ввод, неправильные настройки и сохранение состояния после ошибки.
- Если результат должен быть независим от порядка данных, проверять перестановки.
- Для времени проверять касание концов интервалов, секунды, полночь, вложенные и цепочечные пересечения.
- Для больших чисел проверять выход за диапазон `int` и защиту от переполнения используемого типа.
- Сохранять существующий тестовый runner; при добавлении сценариев обновлять число регистраций, README и подпись CI.
- В бенчмарке использовать результат расчёта и проверять его, чтобы измеряемая работа действительно выполнялась.
- Проверку ожидаемых значений в бенчмарке выполнять вне измеряемого участка.
- В README точно описывать, что измеряет бенчмарк, включая создание менеджера и копирование данных, если они входят в замер.
- При изменении публичного поведения обновлять русский и английский разделы README, значения в примерах и настройки API.

## Проверки и Git

- Для изменений библиотеки проверять Debug и Release со статической и динамической линковкой на доступной платформе.
- Проверять изменённые C++-файлы через clang-format с конфигурацией проекта и выполнять `git diff --check`.
- Использовать clang-tidy, когда он доступен; различать ошибки, предупреждения новых изменений и прежние предупреждения.
- Не повторять уже прошедшие проверки без новых изменений, ошибок или конкретного нерешённого вопроса.
- Для изменения только документации достаточно проверить её содержимое и оформление; сборки и тесты повторять не требуется.
- Если пользователь запретил тесты или бенчмарк, не запускать их и явно обозначить границу проверки.
- Не выдавать локальную проверку Windows/MinGW за проверку Linux или MSVC.
- Не создавать коммиты, не отправлять изменения и не менять индекс без явного запроса пользователя.
- Сохранять существующие изменения пользователя и оставлять выполненную работу в рабочем дереве для просмотра.
- Сообщать о ходе работы кратко: найденная причина, принятое решение, результат проверки и следующий шаг.
- Не запрашивать повторное подтверждение обычных действий, уже входящих в задачу.
